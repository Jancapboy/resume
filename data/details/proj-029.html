🔁 排程不该是「打开页面算一次」

Meridian 原本的排程是一次性的：打开页面，跑一次求解器，看到一张甘特图。但项目推进的真实节奏是状态一直在变——有人开工、有人交付、有人把进度推到 100%。当排程结果只在「打开页面那一次」正确，它在工程上就是错的。这个项目把求解器从页面搬到了服务端，让排程变成随状态自动重算的闭环。

链路

六步闭环

改任务状态 → 写入 OpLog → 服务端从 OpLog 推导当前状态 → 调用 CP-SAT 重排 → 把新排程写回 OpLog 广播 → 各端甘特图实时更新。全链路无人工触发。

  • 状态变更的唯一入口是 OpLog，服务端不读别的状态源
  • 推导与求解分离：derive_state 负责语义，solver 只管约束
  • 结果写回 OpLog 而非旁路推送，事件流始终是唯一事实来源
  • 排程指纹比对，相同则不广播，避免无意义刷新
语义

三条重排规则

重排不是「把没做完的重新排一遍」这么朴素。三条规则分别对应三种真实业务语义，全部写进求解器模型而非上层过滤。

  • done 固定占用资源：进度不能倒退，已完成任务必须留在原时间轴上
  • doing 保留当前 start 作为 release_time：正在做的事不轻易挪动，做最小扰动
  • 进度到 100 自动置 done：消除「状态 doing 但进度 100」的矛盾态
  • 字典序三阶段 P1→P2→P3，每阶段锁定上阶段最优值，而非加权求和近似
根因

容量违规的真因

第一版把已完成任务从模型里剔除，结果排出 8 处容量违规——REV 资源容量为 1 却被排了 2 个重叠任务。根因不是漏了校验，而是求解器根本看不见那个任务还占着资源。

  • 直觉解法：加一个后置校验，发现重叠就报错
  • 正确解法：给 solver 加 fixed_intervals 支持
  • 用 NewFixedSizeIntervalVar 建常量区间，参与同一条 AddCumulative 约束
  • 约束写进模型，才不会漏判——事后校验永远只能兜住已发生的错误
接口

新增 API 与事件

新增 GET /meridian/api/schedule 与 POST /meridian/api/reschedule 两个接口，以及 schedule.update 事件；前端 runtime 补上对应的 applyOp 分支后，甘特图才会跟着动。

  • GET /api/schedule 返回 makespan / objectives / pinned 等聚合指标
  • POST /api/reschedule 触发一次重排并广播
  • schedule.update 事件携带任务级排程变更
  • 漏掉前端 applyOp 分支 = 后端全对、界面不动

🐛 踩过的坑与根因

现象 根因 修法
容量违规 8 处 已完成任务被剔除，求解器看不到它占资源 fixed_intervals + NewFixedSizeIntervalVar
HTTP 接口 500 asyncio.create_task 在 API 路径没有 event loop 改 async def + await broadcast
Caddy 条件重启失效 先覆盖再比对，且临时文件已提前删除 比较必须在覆盖前，临时文件最后清理

💡 最后一条最值得记：13440 根路径 502 时，Caddy 日志里反向隧道（18931）的失败记录只有 01-22 的 4 次，11-11 当天零次——服务器自测公网 IP 的报错与本次部署毫无关系。定位问题要选对观测点，服务器自测公网 IP 是典型的错误观测点。

📌 三条可迁移的结论

原则 1

约束要写进模型，不能写在校验里
事后校验只能兜住已发生的错误

原则 2

重排要最小扰动，不是推倒重来
doing 任务保留 start 作为 release_time

原则 3

事件流必须是唯一事实来源
结果写回 OpLog，别开旁路推送
