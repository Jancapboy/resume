⚡ 全链路四段

把「访客填表 → 收到微信」这条链路从纯前端 mock 改成真实可用的服务端投递：表单 POST 到 EdgeOne Pages 边缘函数，函数在边缘节点读取服务端环境变量里的推送密钥，命中任意一条推送通道即视为成功。

段 1

前端表单提交

访客填写需求表单，前端先做一次预热 GET 再正式 POST，绕开 EdgeOne 首次访问的鉴权重定向。

  • POST /api/contact，body 上限 1MB
  • 先预热种 HttpOnly cookie，再不带 token 正式提交
  • 失败时降级为 mailto: 唤起邮件客户端，线索不丢
段 2

边缘函数网关

函数跑在腾讯边缘节点，冷启动毫秒级；平台约束直接倒逼架构选型。

onRequest(context) context.env context.request context.params
  • 函数包 5MB / 请求体 1MB / CPU 200ms（I/O 不计时）
  • 仅 JS ES2023+，加 package.json 后 CLI 自动识别 fullstack
  • 密钥只从服务端环境变量读，绝不下发前端
段 3

三通道推送

企业微信机器人 / Server酱 / PushPlus 三条通道并行尝试，任一成功即算成功，全部失败才返回 502。

  • 三通道任一成功即返回成功，全部失败才 502
  • Server酱实测返回 code:0 error:SUCCESS
  • 企业微信 Webhook 返回 errcode:93000 即为地址无效，链路本身通
段 4

安全与限流

公网可访问的表单接口必须自带来源白名单与频率限制，否则会被当成免费群发通道。

  • ALLOWED_ORIGINS 同时校验 Origin 与 Referer
  • 同 IP 60 秒内最多 5 次，超限直接拒绝
  • 线上 /.env 与 /.edgeone/project.json 均 404，未泄露

✅ 端到端实测结果

不是设想，以下是镜像站同源提交与主站跨域提交的真实返回。

📊 各场景实测

场景 结果 说明
Server酱 API 直调 code:0 error:SUCCESS 推送通道本身验证通过

🧨 两个真正踩过的坑

第一个坑是协议级的，第二个坑是配置级的，都不看文档基本踩不出来。

🔧 故障与解法

坑 1 · 302 丢 body

Fetch 规范下 301/302/303 把 POST 改写成 GET
重定向后 URL 被剥掉 token，后端收到空 body 报 400

解法 1

先 GET 预热，再不带 token POST
同源 fetch 自动带 HttpOnly cookie，不再触发重定向

坑 2 · CORS 拦截

Access-Control-Allow-Origin 写 * 会挂
credentials:'include' 的跨域请求被浏览器直接拦下

解法 2

回显具体 Origin + Allow-Credentials
配合 ALLOWED_ORIGINS 白名单双保险
