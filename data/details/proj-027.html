🚧 给 Agent 装上闸门：四态决策而非二元开关

Agent 编排最危险的地方在于「它下一步要做什么你拦不住」。这个项目把治理做成运行时的一部分：每个节点执行前后、以及最终对外输出前，都要过一道可插拔门禁。门禁不是 approve / reject 的二元开关，而是四种语义完全不同的决策。

四态

PASS / BLOCK / CHALLENGE / ROUTE

四种决策对应四种完全不同的后续流程。其中 CHALLENGE 的恢复语义是最容易做错的一环。

  • PASS：可改写上下文继续执行
  • BLOCK：立即终止运行
  • CHALLENGE：挂起，等人工审批后恢复
  • ROUTE：切换到另一条分支
  • 恢复时用 Run.PendingGate 记住是哪道门禁挂起的，跳过它——否则重复调 LLM、重复扣配额
位置

三个介入点

治理插在流程里而不是外挂在外围，每道门禁知道自己「能做什么判断」。

  • pre_node：能不能做（开工前）
  • post_node：做完能不能用（产出后）
  • pre_final：能不能对外输出（最后一道闸）
  • 门禁自身故障时默认 fail_open=false，即阻断——安全侧优先
审计

哈希链让门禁不可绕过

每条裁决写入审计表，hash = sha256(seq | prev_hash | 规范化内容) 逐条串联。

  • 改动或删除任意一行，其后所有行的 prev_hash 校验全部失败
  • 这是「门禁不可绕过」的技术底座，而非日志里的一句承诺
  • 纯 Go SQLite（modernc.org/sqlite v1.60.1）免 CGO，单文件部署
门禁库

内置七类门禁

通过注册表装配，可插拔扩展，每类都有独立单测。

  • authz 角色 / 租户 / Claim 鉴权
  • quota 租户配额检查与扣减
  • cost 单次运行成本熔断
  • risk 提示注入与越权检测
  • policy PII 脱敏与合规策略
  • approval 人工审批与二次确认
  • identity 七问身份声明校验与责任主体核对

✨ 特效即数据：用门禁体系自建站点做验证

要验证门禁体系是否真在运行，最直接的办法是用它建一个站。但不让 LLM 直接写 HTML——它只产出结构化 JSON 规格（标题 / 副标 / 区块 / 配色），渲染由受控代码完成：既拿到 LLM 的创意与文案能力，又守住安全边界（渲染层 HTML 转义）与结构一致性。

🔮 每个视觉元素都对应一条真实裁决

视觉效果 对应的门禁裁决
粒子沿决策链流动 每次裁决产生粒子
冲击波 BLOCK
冻结环 CHALLENGE（视觉上「卡住」）
分叉光带 ROUTE
右上角徽标 实时 hash chain 自证

💡 判断特效是否为真的标准：关掉数据库，页面就空了。如果视觉元素与真实裁决无关，那它只是动画。实测运行 45 秒产生 17 次裁决：{'PASS': 7, 'BLOCK': 6, 'CHALLENGE': 3, 'ROUTE': 1}，审计链完整。

🚦 四阶段流水线，每阶段门禁守护

站点构建被拆成四个阶段，每个阶段都有对应门禁在把关——不是最后统一审一次。

spec

LLM 出规格

产出结构化 JSON 规格（标题 / 副标 / 区块 / 配色）。

  • cost 门禁：成本熔断
  • risk 门禁：提示注入与越权检测
render

受控渲染

渲染由受控代码完成，HTML 全转义。

  • policy 门禁：PII 脱敏与合规
  • 结构一致性由代码保证，不靠模型自觉
vision

动效装配

把裁决映射为视觉元素。

  • authz 门禁：谁有权限发布
ship

落盘对外

最终对外确认。

  • approval 门禁：人工审批与二次确认

📌 三条可迁移的结论

原则 1

审批型门禁必须记住「是哪一道」挂起的
否则恢复时重复调 LLM、重复扣配额

原则 2

门禁自身故障默认应阻断
fail_open=false，fail_open 意味着绕过

原则 3

用真实数据驱动特效，才算验证了系统
关掉数据库页面就空了，这是自检标准
