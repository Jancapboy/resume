🏗️ 先把 Dify 跑起来，再谈 Agent 编排

这个项目分两段：先把 Dify 1.19 在本机私有化跑通并自建代理补齐模型供应商缺口；再把 agent 集群从「一堆单节点 chatflow」重构为单应用多节点并行扇出，最后把审计集群部署到服务器给电商数据平台当评审守门人。

🔌 自建 ocproxy：49 行补齐模型供应商缺口

官方接入方式不满足实际需求，于是自己起了一个代理。这不是「造轮子」，而是只有 49 行却精确解决了三个具体问题。

代理

路径改写 + 补头

docker/ocproxy/server.js（node:22-alpine）把 /v1/* 原样转发到上游 /zen/go/v1/*，并补上 x-opencode-session 头（值取 OC_SESSION，默认 dify-local-01）。

  • SSE 流式不缓冲，避免被代理攒成整段才吐
  • 容器内 8080、宿主机 8799（EXPOSE_OCPROXY_PORT）
  • 写在 override 文件里，compose 自动合并，up -d 就会一起起
模型

openai_api_compatible

模型供应商用 openai_api_compatible 接 deepseek-v4.1-flash，Base URL 填 http://ocproxy:8080/v1。

  • 必须填容器网络地址，不能填 localhost
  • 凭据只存 Dify 数据库加密，本机临时凭据已清理
免费额度

订阅额度的真实边界

实测踩出免费模型的两种失败形态：*-free 返回 429 FreeUsageLimitError（Retry-After 约 18 小时），非 Go 的付费模型返回 402 Insufficient balance。

  • 根因：Go 订阅只覆盖 Go provider 的请求
  • 因此只用 /zen/go/v1 + Go 覆盖的模型

🔀 集群形态重构：第一版为什么是错的

初版把每个 agent 做成独立 chatflow（各 1 个 LLM 节点），编排逻辑甩给外部 Node 脚本。问题很直观：Dify 里看到的全是空壳，边界和模型归属都不在应用内，改一个判据要动两个地方。

🏛️ 两种形态对比

维度 初版：一堆单节点 chatflow 终版：单应用多节点
应用内可见性 每个应用只有 1 个 LLM 节点，是空壳 start → 4 个 LLM 节点 → 汇总 → answer
模型归属 在外部脚本里，界面上看不到 每个节点自带独立 model
判据边界 混在外部配置，易串味 节点提示词只含自己那部分判据
编排位置 外部 Node 脚本，跨系统 全在 Dify 应用内，一个地方看全
并行度 start 并行扇出到 4 个 LLM 节点 汇总走 template-transform 节点

💡 回答节点的一个坑：template-transform 的输出变量名是 output，answer 里必须写 {{#tpl.output#}}；写成 text 会把字符串原样打印出来。

闸门

按节点切 YAML 并校验不串味

DSL 的 node 块以 - data: 起、id 在块尾，切错位置会整体错位。除了结构校验，还额外加了一条语义校验：本节点提示词里不许出现别人的判据。

  • 结构错位在导入前就被挡住
  • 语义串味在生成时就报错，不留到运行期
导入

dsl import 的更新语义

带 app_id + draft_hash 才是更新，否则会重复建应用。这条不看文档基本踩不出来。

  • 更新与新建是两种不同语义，参数决定行为
  • 误用会得到一堆重复应用
删除

console API 的鉴权组合

删应用用 DELETE /console/api/apps/{id}，必须带 Cookie: access_token=..; csrf_token=.. 加 X-CSRF-Token 头。用 curl -b 读 cookie 文件的方式会 401。

  • Cookie 与 CSRF 头缺一不可
  • cookie 文件方式与 Cookie 头方式不等价

🚧 部署期三个协议坑，逐个实测定位

这三处的共同点是：报错信息完全不指向真实原因，只能靠读协议与读代码定位。

🧩 现象 → 根因 → 修复

现象 根因 修复
LLM 节点有 token，但 HTTP 节点 retry 两次后 failed HTTP Request 节点打 host.docker.internal 被 SSRF 防护拒 422（LLM 节点不受影响，所以看起来像「模型能调、接口不能调」） docker/.env 加 SSRF_PROXY_ALLOW_PRIVATE_IPS=<compose 网段>,192.168.0.0/16,127.0.0.1，再 up -d api worker plugin_daemon
difyctl 写 login.yml.lock 报 EPERM 受限沙箱里 %APPDATA% 不可写 DIFY_CONFIG_DIR 指到可写目录并复制 tokens.yml / login.yml
dsl import 的 http 节点报 invalid body data body.data 只能有一个 item 拆成单 item
改完 .env 要不要重建镜像？ 配置走环境变量注入，不在镜像里 不需要重建镜像，重启对应容器即可

💡 SSRF 那条最容易误判：因为 LLM 节点完全正常，只有一小部分节点失败，很容易被当成「模型不听话」或「接口地址写错」，实际是防护把私网地址拦了。

🛡️ 审计工位落到服务器：16 条判据当守门人

集群建好之后把它接到电商数据平台 ecdata 上，作为评审守门人。形态是服务器端常驻服务 + 反向隧道回调本机 Dify，隧道断了直接 fail-closed。

🔗 完整链路

环节 实现
入口 https://115.159.190.72/audit/（health / pending / ledger 三个接口）
服务 systemd ecdata-audit，代码 /opt/ecdata/audit/audit_worker.py（465 行），监听 127.0.0.1:8790，由 Caddy 暴露 /audit/*
链路 Meridian 任务 review → 拉 ecdata 契约 / 健康 / 表结构 → 经反向隧道 18080 调本机 8080 的 Dify → 16 条判据 → 写回 Meridian（done / blocked）+ ecdata /agent/report + ledger
判据 A1 结构 / A2 数据 / A3 安全 / A4 交付，四域共 16 条
隧道 本机双击启动审计隧道.cmd（python tunnel.py），断了直接 fail-closed
实测（E1） 16/16 判据完整，2 条 FAIL（R1-03 / R1-04），31s，耗 21971 tokens，Meridian 变 blocked

💡 「材料里没有代码，所以 A3 多为 unknown」是对的：没有证据的判据写 unknown 并说明缺什么，而不是让模型猜一个结论 —— 这比假装审过了要安全。

首审

12/16 与 16/16 的差别

E1 首次审计时材料缺 token，只有 12/16 判据有回、其余为 unknown，任务停在 review；补齐材料后复审拿到完整 16/16 并出现 2 条 FAIL。

  • 缺材料时停在 review 而不是硬判
  • 复审才给出可执行的 FAIL 结论
结果

双写回 + 留痕

审计结论同时写回两个系统：Meridian 侧把任务标成 done 或 blocked 让排程继续或卡住；ecdata 侧落 /agent/report 与 ledger 供后续追溯。

  • blocked 会真的挡住任务，不只是留个记录
  • ledger 记状态、失败原因与计费状态
韧性

失败要向安全侧倒

反向隧道由本机手动启动，进程被杀或网络中断都会导致服务不可用。因此隧道断开时服务直接 fail-closed —— 宁可停审也不放行。

  • 审不了 ≠ 审过了
  • 不可用状态显式表达，不与「通过」混淆

📌 三条可迁移的结论

原则 1

平台内的编排才能被平台内的用户看懂
外部脚本编排 = 界面上的空壳

原则 2

部分节点失败要先怀疑防护而非模型
SSRF 拦私网，LLM 节点不受影响

原则 3

守门人不可用时必须 fail-closed
审不了不等于审过了
