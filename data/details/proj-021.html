🌍 核心命题：把「打不开」拆成网络层还是服务端

用户反馈「站点打不开」时，最容易犯的错是直接去查服务端。但如果网络层根本不通，查服务端永远查不出问题。这套体系的全部价值，就是用公开探针在真实分布式的节点上实测，把这个问题一次性定死。

工具

双通道探针

两个探针服务互为备份，且均无需账号，脚本可直接跑。

check-host.net globalping.io
  • check-host：一次铺开多个境外节点
  • globalping：可指定国家 / 城市 / 网络
  • 两者都返回节点级状态码与耗时
脚本

check_reachability.py

三个探测目标（主站 / 详情页 / EdgeOne 镜像）跑一遍，输出结构化结果。

  • 国家维度：CN / HK / SG / US / JP
  • 每节点打印状态码、状态名、total 耗时
  • 失败节点直接打印 rawOutput 便于归因
归因

网络层 ≠ 服务端

可达性实测与构建历史两条证据交叉验证，把问题定位到具体层面。

  • 22 个境外节点全 200 → 服务端健康
  • 中国大陆 5 节点全通 → 网络层可达
  • 结合 Pages 构建历史 → 排除服务端故障

📊 实测结果：22 节点全 200，中国大陆 5 节点全通

用 check-host.net 对三个页面做分布式探测，共 22 个节点全部 HTTP 200；再用 globalping 专门打中国大陆节点，全部 ping 通。

📈 check-host.net 节点分布

探测目标 节点数 HTTP 200 结论
GitHub Pages 主站 7 7 / 7 全部成功
GitHub Pages 详情页 8 8 / 8 全部成功
管理后台 7 7 / 7 全部成功

💡 节点代码前缀即国家（de1 / hk1 / jp1 / sg1 / us5…），check-host 的结果是数组 [成功?, 耗时, 状态, HTTP码, IP]，按位置解析即可拿到节点归属。

🎯 归因结论与由此产生的决策

三条独立证据交叉验证，最终把结论钉死，并且直接改变了架构决策。

结论

主站在国内属「可达但无加速」

  • 22 个境外节点全 200 → 服务端健康
  • 中国大陆 5 节点 ping 全通 → 网络可达
  • 延迟 148~251ms → 无 CDN 加速
决策

加速只能靠独立镜像

  • GitHub Pages 无国内 CDN
  • EdgeOne 中国站镜像承担加速职责
  • 镜像令牌失效属平台限制，非站点故障
观测

构建历史连续性

Pages 部署历史逐次核对（UTC），连续无中断：

  • 23:46 / 01:57 / 04:08 / 06:21 / 08:00 / 08:30
  • 每一次构建状态均为 built
  • 配合探针实现每次发布后的即时回归

🐛 探针本身的两个坑

工具用起来也有陷阱，踩过一次就会记住。

🔧 globalping 使用注意

坑 现象 解法
http 类型 target 被拒 "does not match any of the allowed types" 用 ping 类型即可
结果结构误判 timings 是 list，.get() 会炸 按 probe.country / city / network 取，用下标读 timings
账号要求 以为需要注册 两者均无需账号，脚本可直接调

💡 附带解决的一个真问题：本机 git 全局配置了 http.proxy = http://127.0.0.1:7890，但 Clash 进程退出后该端口只剩 FIN_WAIT_2、无 LISTENING，导致所有 push 直接 ECONNREFUSED。清除全局代理后直连实测 git ls-remote origin main 1.5 秒成功。

📌 三条可迁移的结论

原则 1

先分清网络层还是服务端再动手
否则会一直查错的东西

原则 2

用公开探针取数据，不要靠推测
22 节点实测比一句「应该是正常的」有说服力

原则 3

可达 ≠ 快
148~251ms 说明问题在加速而非连通
