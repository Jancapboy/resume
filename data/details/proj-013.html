🔁 流水线四段式

以自研 RSS 生成器 ForgeRSS 为采集端，把「信息源 → 结构化知识节点」做成一条可增量、可审核、可持续的自动化流水线，为运维知识库 TO B 商业化提供数据底座。

段 1 · 采集

ForgeRSS 定向采集

自建 RSS 生成器，按目标站点结构定制抓取规则，避开通用阅读器的字段缺失问题。

  • 已接入 anthropic_news / anthropic_engineering / openai_research / ai_coding
  • 单源 8~10 篇稳定抽取
  • 免登录源全自动，扫码类源人工兜底
段 2 · 清洗

结构化归一

统一正文抽取、Markdown 归一与元信息补全，保证入库内容格式一致、可被检索。

  • 正文抽取 + Markdown 规范化
  • 标题 / 时间 / 来源元信息补全
  • 工具链：rss_to_kb.py、feed_to_kb_entry.py
段 3 · 入库

知识节点注册

经 kb_add 注册为知识节点，并与既有主题节点建立关联，形成可扩展的图谱。

  • 节点规模 13 → 15
  • 与 model-thinker-framework 等主题节点关联
  • 节点 ID 命名规范（源名连字符化）
段 4 · 审核

Curator 质量流转

新节点默认 unrated / unseen，由 Curator 审核评级后才进入正式知识消费链路。

  • unrated → rated 状态机
  • 待审队列可视化
  • 审核后才计入可用知识

🧱 环境工程：让 Docker 在国内网络跑通

Windows + WSL2 + Docker Desktop + 本机代理的组合是典型的四层网络坑，逐层定位后三件套同时生效才稳定跑通大镜像与容器构建。

🔍 故障演进与根因

现象 根因 处置
EOF / failed to resolve metadata daemon 内置代理指向不可达地址 改手动代理配置
dial tcp 202.53.x.x:443: connectex 直连被墙，代理未生效 ProxyHTTPMode = manual
172.30.0.1:7890 actively refused 代理只监听 127.0.0.1，WSL 侧不可达 mihomo allow-lan: true

💡 关键认知：Docker 引擎跑在 WSL2 虚拟机内，127.0.0.1 指向的是 WSL 自己而非 Windows 宿主，必须用 172.30.0.1 网关地址；allow-lan: false 是最隐蔽的一环。

🧩 稳定运行三件套

① 代理放行

mihomo allow-lan: true
允许 WSL 侧接入 7890 端口

② 地址纠正

172.30.0.1:7890
用宿主网关地址，不用 127.0.0.1

③ 镜像加速

registry-mirrors
国内 CDN 直连，绕过代理不稳定

④ 构建注入

build-arg 代理
容器内 apt/wget 不走镜像源，需显式注入
