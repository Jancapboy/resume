🔑 比报告更严重：三个令牌全是失效值

用户报告「令牌刷新任务只改 projects.json、不重新注入三处内联兜底块，导致 index.html 里的令牌停留在旧值」。实测后发现问题比报告更严重：不是简单的不一致，而是三处令牌全部 401 失效。主站 GitHub Pages 免令牌不受影响，只有 EdgeOne 镜像被鉴权拦住——这正是国内访客走兜底渲染时表单静默失败的根因。

🧨 三层根因，不是一层

表面是「忘了注入」，往下挖还有时序陷阱和镜像快照两层。只补注入仍会在部署后再次失效。

根因 1

缺注入步骤

refresh_contact_token.py 第 3 步只用正则替换改 projects.json，从头到尾没调用 inject_inline_data.py——造成慢性漂移，内联块永远停在旧值。

  • 症状：index.html 内联块令牌过期 27 小时
  • 本质：写路径只覆盖一个文件，漏了三个
根因 2

注入时序陷阱

注入必须排在部署之后。部署会作废旧令牌并签发新令牌，新令牌只有部署完成才存在——注入在部署前等于注入一个即将作废的旧令牌，比不同步更糟。

  • 结论：内联块永远只能持有「上一次部署」的令牌
  • 自洽性：令牌有效期 3h < 刷新间隔，设计上成立
根因 3

镜像令牌是部署快照

镜像目录的令牌是部署时快照，SITE 改完不同步到 MIRROR，导致镜像的 json 与 HTML 也各自为政。

  • 修复：把「同步镜像」移到注入之后
  • 末尾另加一次新令牌实测

🍪 逆向 EdgeOne 鉴权机制

调试中反复踩到 401 / 405，根因是没搞清 EdgeOne 的鉴权链路。查证后确认：靠带 token 预热 → 下发 HttpOnly cookie → 后续带 cookie 访问，token 本身不直接放行请求。

🔧 现象 → 根因 → 正确做法

现象 根因 正确做法
裸访问带 token 的 URL → 401 没有 cookie，token 不直接放行 先带 token 预热种 HttpOnly cookie
带 token 的 POST → 405 仅支持 POST 302 重定向下 Fetch 把 POST 改成 GET 并丢 body 同源直 POST 相对路径
跨源表单提交被拦 预热与正式请求需分离地址 先预热拿 cookie，再用不带 token 地址 POST
误报 405 是前端缺陷？ 测试脚本没复刻预热步骤 js/ai.js 的 postToApi() 本就实现正确

💡 别冤枉前端：真实缺陷在测试脚本没走预热流程，而 js/ai.js 的 postToApi() 早已正确实现了「预热拿 cookie → 不带 token 地址正式 POST」，无需改动。

🛠️ 工具链补强与闭环

修复不是补一次值，而是把「写入→注入→断言→同步→实测」做成不可跳过的闭环，让同类漂移在提交前就被拦住。

工具 1

inject_inline_data.py

加 --check 模式 + 注入后自动一致性自检，不一致立即退出，避免错误值落盘。

  • 注入 index / project / admin 三处
  • 自检不通过 → 退出码非 0
工具 2

check_token_consistency.py

新增：逐处列出 10 个令牌来源 + 比对 + --live 实测，一眼看散落全貌。

  • 覆盖 SITE / MIRROR 各来源
  • --live 直接打真实端点验活
工具 3

refresh_contact_token.py

插入第 3.5 步注入 + 第 3.6 步一致性断言（不一致拒绝提交），第 4 步同步镜像移到注入之后。

  • 断言失败即中止，不带病提交
  • 末尾对新令牌做一次实测

📌 三条可迁移的结论

原则 1

写路径覆盖几个文件，就要校验几个
只改一处 = 慢性漂移的起点

原则 2

注入时序要跟着「令牌何时才存在」走
部署后才签发新令牌，注入必须排其后

原则 3

先复刻鉴权链路再判定前端缺陷
405 是测试脚本漏预热，不是 code bug
