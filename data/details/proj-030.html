📱 「老板在微信群里 @ 一个能干活的 AI」

需求很具体：老板在个人微信群里 @ 一个能查状态、下指令、跑工具的 AI 助手。但这条路上有一个很容易踩的坑——官方渠道插件的能力边界。个人微信与企业微信常被混为一谈，「官方支持个人微信」不等于「官方插件支持群聊」。这个项目做的就是把边界查清楚，把方案定下来。

实测

不看宣传，看源码

自写 check_channel_group_support.py 下载插件 tarball，逐项检查四件事：groupPolicy 默认值、会话类型是否写死 direct、群相关 API 标识频次、README / CHANGELOG 群聊声明。插件升级后可随时复验。

  • 判据是默认值而不是「有没有群聊相关代码」
  • 会话类型写死 direct 是最硬的否定证据
  • README 声明与源码实现分开统计，防止宣传口径混淆
  • 脚本自动定位 npm（WorkBuddy 内置 Python 的 PATH 会截断）
对照

两个插件的实测结论

本次实跑脚本的完整输出：

  • 个人微信 v2.4.10：groupPolicy ['disabled']、会话类型 ['direct']、群相关标识零命中、README 与 CHANGELOG 群聊记录各 0 次 → 确实不支持群聊
  • 企业微信 v2026.10.30：groupPolicy ['allowlist','open']、chatId 命中 169 次、README 声明群聊 8 次 → 支持群聊
  • 同一个插件包，两套完全不同的群聊能力
纠错

两次说错，两次更正

选型过程中我自己的两次口误，都被源码证据推翻——这类错误如果不查源码就会一路错到部署：

  • 第一次错：说「openclaw 只能接个人微信」→ 错，接私聊完全没问题（腾讯官方插件），只是那个插件不支持群聊
  • 第二次错：说「个人微信已支持群聊」→ 也错，源码为证确实不支持
  • 准确结论：官方微信插件只支持私聊；个人微信群聊必须走 Wechaty 这条路
  • 两次错误的共同点：都是拿「一个插件」推「整个生态」
落地

LightAgent 真跑通

选型不是看 README 宣传——把仓库 clone 下来逐文件看，并且真的把侧车跑起来。

  • LightAgent（MIT / Python / 23 stars），wechat4u puppet 在 2026-11 仍能成功输出微信登录二维码
  • 侧车 8 个 .mjs 模块共 2,933 行，node --test 实测 61 项测试全部通过（467ms）
  • Python 侧依赖轻（numpy / aiohttp / requests 等基础库），无重型 ML 框架
  • 微信群通道目录 64 个 Python 模块共 26,778 行——工程级而非玩具级

⚖️ puppet 路线实测对比

个人微信群聊的技术路线全部依赖 Wechaty 的 puppet（协议实现层），puppet 的存活状况是决定性因素。

📊 各 puppet 路线可用性（2026-11 实测口径）

Puppet 协议 可用性 封号风险 成本

🏗️ 架构决策：分工，而不是迁移

最终方案是两个系统各司其职，而不是把已有能力推倒重来。

🔀 通道分工与风险对策

角色 承担 说明
LightAgent 微信群入口 承接个人微信群消息与 @ 事件
OpenClaw 执行 已有 5 个 agent / 飞书 4 账号 / 工具链 / 工厂机器人面板，不动
企业微信 零风险兜底通道 已配 groupPolicy=open、dmPolicy=pairing，任一通道异常不影响整体

💡 为什么不迁移：OpenClaw 侧已有 agent、账号、工具链与面板，把微信群能力迁进去等于重写；让 LightAgent 只做「入口」、OpenClaw 只做「执行」，两边互补，改动面最小。

📌 风险与对策：写进文档，不留到上线后

风险 1

所有免费 puppet 都被官方重点打击

对策 1

再叠加随机延迟，避免行为熵坍缩

不存在零风险方案，账号风险是真实的
